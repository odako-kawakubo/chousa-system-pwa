# chousa-system-pwa

アスベスト調査システムPWA（本開発版）

## このプロジェクトの位置づけ

既存のPWAプロトタイプで確立した画面・操作・業務ロジックを引き継ぎつつ、コード構造と同期基盤を整理して作り直す本開発プロジェクトです。

旧プロトタイプは仕様確認と参考実装として保存し、新プロジェクトでは後付けの関数上書きや多重定義を行わず、役割ごとのモジュールとして実装します。

## 現時点の確定方針

### 1. 案件の識別

- 案件番号は重複しない運用とする
- 案件番号をシステム上の一意キーとして使用する
- 案件名は表示・検索用として使用する
- ランダムな案件IDは原則使用しない

例：

```text
案件番号：260805-001
案件名　：○○工場 改修工事
```

### 2. 既存の業務構造を維持する

次の関係は変更しません。

```text
仕上表 ↔ 建材レコード ↔ 建材リスト
```

- 仕上表：建材を入力・配置する画面
- 建材レコード：仕上表と建材リストで共有する基礎データ
- 建材リスト：建材情報を一覧で確認・編集する画面
- 写真、採取、分析などの既存仕様も、現行プロトタイプを基準に引き継ぐ

新しいID体系や業務概念を追加することは、現段階では行いません。

### 3. オフライン利用を前提にする

- 通信状態にかかわらず、現場で入力・編集できることを必須とする
- 操作内容はまず端末内へ保存する
- オンライン時にFirebaseと同期する
- 通信失敗によって入力内容を失わない構造にする
- Firebaseへの接続状態が、画面操作を止めないようにする

### 4. Firebaseの役割

- Firestoreは複数端末間の同期先として使用する
- 送信処理と受信処理を分離する
- 変更対象だけを送信する
- 受信listenerは必要な範囲だけ接続し、不要な再接続を繰り返さない
- 保存失敗、手動同期、画面表示処理からlistenerを操作しない

詳細設計は、既存プロトタイプの実際のデータ構造と動作を確認したうえで確定します。

### 5. コード管理

- 開発時は役割別の複数ファイルで管理する
- 同じ関数名を複数回定義しない
- 既存関数を後段で再代入しない
- `wrap()`による機能追加を行わない
- 表示関数に保存・同期・再接続の副作用を持たせない
- 各機能からFirestoreを直接操作せず、同期モジュールへ集約する
- 公開用ファイルを一本化する場合は、手作業ではなくビルド処理で生成する

## 各ファイルの役割

### `src/00_boot.js`

アプリ起動、初期化順序、Service Worker登録などを担当します。

### `src/10_config.js`

バージョン、Firebase設定、共通定数、コレクション名などを管理します。

### `src/20_state.js`

現在開いている案件、画面状態、共通のアプリ状態を管理します。

### `src/30_local_store.js`

端末内保存とオフライン利用の基盤を担当します。

### `src/40_sync.js`

Firestoreへの送信、Firestoreからの受信、案件接続などを集約します。

### `src/50_material_record.js`

建材レコードに関する処理を担当します。

### `src/60_shijo.js`

仕上表に関する処理を担当します。

### `src/70_material_list.js`

建材リストに関する処理を担当します。

### `src/80_photos.js`

写真の撮影、保存、表示、関連付けに関する処理を担当します。

### `src/90_ui.js`

画面描画、ボタン、モーダル、イベント処理を担当します。

## 初期開発の進め方

1. 旧プロトタイプの画面・データ・処理を整理する
2. 新プロジェクトへ移す機能と、そのまま残す仕様を確定する
3. ローカル保存と案件選択の基盤を作る
4. `仕上表 ↔ 建材レコード ↔ 建材リスト`を順番に移植する
5. Firebase同期を接続する
6. 写真、採取、分析、出力機能を段階的に移植する

現段階では、機能コードを急いで実装せず、構造と責任範囲を固めることを優先します。
