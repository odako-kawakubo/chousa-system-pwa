# v0.1.6.2H strict review

## Scope

v0.1.6.2 を土台に、仕上表の Firestore 保存を「全件保持」から疎保存へ変更し、
finishRecord の物理 delete を他端末へ伝える短期変更履歴を追加した。

## 保存方式

- 新規案件作成時の空 finishRecord 456件一括 write を廃止。
- 初期構造はアプリ側で生成。
- 通常入力は変更された finishRecord だけ保存。
- 部屋No. / 部屋名は標準末尾 602 の1件に集約。
- ＋階: 追加階の最後の標準部屋の 602 を1件保存。
- ＋部屋: 追加部屋の 602 を1件保存。
- ＋行: 追加行の6番目部位（603/604/...）を1件保存。
- B / S / R / 外部も同じ復元ルールへ統一。
- 初期状態へ戻った内容差分は、構造復元に不要なら物理 delete。
- 構造復元に必要な 602 / 603... は空欄でも保持。

## 復元

1. createDefaultFinishRecords() で初期構造を生成。
2. Firestore の疎 finishRecord の位置から追加階・追加部屋・追加行を補完。
3. 疎 finishRecord の内容差分を上書き。
4. 602 の roomNo / roomName を同じ部屋ブロック全体へ展開。

## finish change log

- finishRecord set/delete は finishChangeLogs への change log と同一 Firestore batch で確定。
- changeId は Firestore 自動ID。
- committedAt は serverTimestamp。
- カーソルは committedAt(seconds/nanoseconds) + changeId。
- delete は change log に recordId + operation=delete を残すため、削除済み本体に updatedAt がなくても他端末へ伝達可能。
- カーソル自身の changeLog Document が残っていることを getDoc で確認し、残っていなければ疎 finishRecord 全件から再構築する。
- 時刻だけで「履歴が残っている」と推測しない。

## 履歴保持

- 変更履歴は expiresAt = 約30日後を記録。
- Firestore TTL には依存せず、案件同期時に24時間に1回まで、期限切れを最大200件整理する。
- 古い端末でカーソル本体が消えていた場合は full sparse rebuild にフォールバック。

## 案件ごとの接触端末

projects/{projectId}/syncDevices/{deviceCode} に以下を記録する。

- deviceCode
- deviceName
- lastSeenAt
- finishChangeCursor

これは履歴削除条件には使用しない。古い端末が永久に履歴整理を妨げないため。

## Bug found during strict review and fixed

Initial H draft selected the highest sixth-part row as the room common-field carrier.
With a +row marker 603 present, 603 could override roomName/roomNo stored on 602.
This contradicted the agreed rule “roomNo/roomName are stored on 602”.

Fixed:
- room common carrier is explicitly the standard 602 record.
- 603+ are row-structure records only.
- structure retention calculates room marker (602) and row marker (603+) independently.

Also fixed:
- when a finish change is queued as unsent, remote changes cannot rebuild the screen from the stale known-Firestore cache and overwrite the local unsent value; restoreKnownFinishRecords overlays the unsent queue before rebuilding.

## Known limitations / next validation

1. Existing G projects that already contain 456 finishRecords are not auto-compacted in H. Automatic mass migration is intentionally avoided because it would generate many deletes/change logs and could affect other devices. Sparse-write benefit is cleanest to verify with a newly created H test project.
2. finishChangeLogs realtime listener still watches “after the session cursor”. Normal reads are proportional to new change-log entries, but a Firestore reconnect may re-evaluate change-log entries accumulated during that open session. This is vastly smaller than listening to all finishRecords, but should be measured on device before calling the listener/read design final.
3. serverTimestamp + changeId cursor accepts the previously discussed extremely rare cross-client ordering risk instead of paying a transaction-based sequential revision cost.
4. Full field-by-field conflict merge remains a later-stage item; H keeps the existing mostly single-owner assumption.
