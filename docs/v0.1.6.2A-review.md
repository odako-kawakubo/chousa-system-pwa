# v0.1.6.2A レビュー

## 今回の目的

v0.1.6.1で作ったFirestore 1レコード保存基盤を、実際の仕上表・建材UIへ接続する。
1端末で「入力 → Firestore保存 → 別案件へ切替 → 同じ案件を再度開く → Firestoreから復元」を確認できる最初の検証版。

写真レコードのFirestore復元は次段階（v0.1.6.2B）で扱う。

## 変更内容

### 1. 仕上表の実保存を接続

以下の編集確定をfinishRecord 1件単位のFirestore保存へ接続した。

- 建材ID/建材名称からのmaterialId紐付け
- 建材紐付け解除（初期状態へ戻す操作を含む）
- その他1/2の実部位
- 部屋No.
- 部屋名

`fieldEditedAt`はFirestoreで競合対象となる項目だけ更新する。
`inputId`は表示・入力補助のため、fieldEditedAt/Firestore差分判定の対象にしない。

### 2. finishRecordの初期状態復帰を実UIから確認可能にした

初期テンプレートに存在するfinishRecordを空欄へ戻し、4項目
`roomNo / roomName / part / materialId` が初期値と一致すると、
既存のRepository判定を通してFirestore側のfinishRecords/{finishId}をdeleteする。

ローカルStoreのfinishRecord自体は削除しない。

### 3. materialRecordの実保存を接続

以下をmaterialRecord 1件単位の保存へ接続した。

- 新規建材登録
- 建材名称
- 調査備考
- レベル
- 分析の要否
- 採取数
- 採取場所1〜3
- 採取日
- 採取済み
- 採取部位
- 仕上表変更から再計算された部位/使用箇所

新規建材登録時は、materialRecordの保存要求を先に積み、続いてfinishRecordの紐付け保存要求を積む。
同一端末内の保存要求はPromiseチェーンで順序を維持する。

### 4. 案件を再度開くとFirestoreから仕上表＋建材を再構築

非サンプル案件を案件一覧から開く際、ローカル案件スナップショットを復元元にせず、以下で再構築する。

```
default-finish-data.js
  + Firestoreに現在存在するfinishRecord差分一式
  + FirestoreのmaterialRecord一式
```

materialRecordを先に再構築してから、finishRecordのmaterialIdに対応するinputIdを復元する。

これにより「ローカルに残っていたから表示が戻っただけ」という確認にならず、Firestore保存→読込を実際に検証できる。

### 5. 未送信保護

Firestore保存に失敗して未送信キューへ残ったレコードは、再読込時にFirestore取得結果の後から重ねる。

- 未送信material set → remote materialより優先
- 未送信finish set → remote finishより優先
- 未送信finish delete → default状態を維持

そのため、Firestore読込を追加しても未送信ローカル作業を勝手に消さない。

### 6. 写真は今回まだFirestore復元しない

案件切替時、写真は従来のローカル案件スナップショットを維持する。
写真のFirestore保存・再読込検証はv0.1.6.2Bで行う。

### 7. その他1/2の入力導線を修正

Firestore実機確認前に、その他1/2の入力ルールを現行仕様へ合わせて整理した。

- 空欄セルをタップしただけ／空欄のまま編集終了しただけでは`part`へ「その他」を入れない
- 部屋コピー時も、コピー元の`part`が空なら空欄のままコピーする
- **新規建材を「登録」した時点で、その他1/2の`part`が空欄なら`part = "その他"`を確定する**
- すでに`part`へ梁・柱・配管等が入っている場合は、その値を維持する

この補完は一般の部位編集処理ではなく、`registerMaterialForCell()`の建材登録確定経路だけで行う。

### 8. その他1/2の部位候補を整理

その他1/2の部位候補から、通常列としてすでに存在する部位を除外する。

除外対象：

- 床
- 巾木
- 壁
- 天井
- 床・犬走（互換表記の「床 犬走」も含む）
- 外壁
- 屋根
- 軒裏
- その他1
- その他2

`その他`は実部位として使用できるため候補に残し、初回から選択できる基本候補として必ず含める。

### 9. 建材名と部位の入力フォーカス連携

その他1/2だけ、明示確定時に同じ入力グループ内の相手セルへ移動する。

```
建材名を候補選択／登録／Enterで確定
  → 部位セルへ移動

部位を候補選択／Enterで確定
  → 建材名セルへ移動
```

単なるblurや別セルのタップでは自動移動させない。ユーザーが意図して移動した先を奪わないため、候補選択・登録・Enterという明示確定時だけ適用する。

## 実機確認手順

### A. 保存→復元

1. 通信可能・ログイン済みの状態で起動
2. 新規案件を1件作成
3. 仕上表で未登録建材を登録し、セルへ紐付ける
4. 建材リストで建材名称または調査備考を変更
5. 数秒待つ
6. 案件一覧からサンプル案件へ切り替える
7. 作成した新規案件をもう一度開く
8. 以下を確認
   - 登録した建材が建材リストへ戻る
   - 仕上表の同じセルへ建材が戻る
   - 建材名称/調査備考が戻る
   - 部位/使用箇所が正しい

### B. 初期状態復帰（Firestore delete）

1. 新規案件の初期セルへ建材を紐付ける
2. Firestore Consoleで該当 `projects/{案件番号}/finishRecords/{finishId}` が存在することを確認
3. 同じセルの建材を解除して初期状態へ戻す
4. 数秒待つ
5. Firestore Consoleで該当finishRecordドキュメントが削除されたことを確認
6. サンプル案件へ切替
7. 新規案件を再度開く
8. 解除したセルが空欄（default-finish-data.jsの初期状態）のままであることを確認

### C. その他1/2入力ルール

1. その他1/2の部位が空欄のセルをタップし、そのまま離れる → 空欄のまま
2. その他1/2へ新規建材名を入力し「登録」 → 部位が空なら「その他」が入る
3. 先に部位へ「梁」等を入力してから建材登録 → 「梁」が維持される
4. 部位候補に床・巾木・壁・天井・外壁・屋根・軒裏等が出ない
5. 部位候補に「その他」が出る
6. 建材名を候補選択／登録／Enterで確定 → 同じ行の部位へ移動
7. 部位を候補選択／Enterで確定 → 同じ行の建材名へ移動
