## Architecture result
### PASS
- Catch-up query is one-shot `getDocs` and is not reused as the long-lived listener.
- Realtime listener starts from per-record-type caught-up cursor.
- A browser `offline` event stops the listener; `online` performs catch-up before reopening the listener.
- F legacy single `lastSyncedAt` is NOT expanded into three cursors; first G open does a one-time full migration read to avoid missing type-specific changes.
- Project snapshots preserve `syncMeta` across project switches.

### IMPORTANT GAP 1 — physical finishRecord deletions
Current structural editing can physically delete old finishRecord IDs (`persistFinishStructureChange` -> `deleteFinishForProject`). A one-shot query based on `updatedAt` cannot discover a document that was deleted while a device was not listening, and a listener query limited to `updatedAt > sessionBaseline` may never have contained an older document, so its later deletion is also not guaranteed to appear as `removed`.

This means the new catch-up model needs one of:
1. finishRecord tombstones/logical delete with updatedAt, or
2. a structure-version marker that forces a finishRecord full refresh when structure changed.

Until that is resolved, +部屋/+階などの structure rekey across multiple devices is not fully safe.

### IMPORTANT GAP 2 — fieldEditedAt conflict merge is not complete
Incoming records are currently skipped when `fieldEditedAt` is identical, otherwise the whole record is replaced. Same-record/different-field concurrent edits are not truly field-by-field merged, and an unsent local record causes the matching remote record change to be filtered. This is compatible with the current mostly-single-writer test stage, but not yet the final multi-device conflict contract.
