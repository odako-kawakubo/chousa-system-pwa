# システム開発 共通運用ルール

対象：調査システムPWA「しらべ」、単体カメラアプリおよび関連する社内システム。  
制定方針：2026-11-06。運用しながら合意のうえ改定する。  
本規定は作業権限と運用フローを定める。技術的な現状・実装済み仕様は現行コード、設定、テスト結果と照合すること。

## 1. 最優先原則

1. **明確な承認がない限り、コード・ブランチ・GitHub設定・Firebase環境・公開先を変更しない。** 不具合報告、解析依頼、相談を実装指示と解釈しない。
2. **継ぎ足しパッチを原則禁止する。** 変更前に責務・データフロー・呼び出し元を解析し、正しい処理へ書き換える。旧処理、重複関数・イベント・CSS・import等の不要物を整理する。必要な互換処理は理由を確認して維持する。
3. 承認された範囲外の仕様変更・機能追加・構造変更を行わない。関連不具合を見つけてもまず報告する。
4. 保存・同期・オフライン・既存レコード・既存ユーザーデータの保全を優先する。テストしていない事柄を「確認済み」としない。
5. レビューと本番を区別し、**既存のレビューURLを勝手に変更・上書き・廃止しない。**

## 2. 標準開発フロー（8ステップ）

| 段階 | 作業 | 許可と確認 |
| --- | --- | --- |
| ① 解析 | 現行コード・仕様書・関連処理・依存関係の確認 | 読み取りのみ |
| ② 方針 | 原因、影響範囲、修正案、検証項目を提示 | ここまで変更禁止 |
| ③ 実装 | 承認された範囲を原則 `work` で修正 | 実装指示後のみ |
| ④ 検証・レビュー公開 | 構文・参照・機能・回帰テスト、承認された固定URLへ公開 | レビュー公開の許可が必要 |
| ⑤ 実機レビュー | ユーザーの確認、同じブランチ・URLで改善反復 | 合意済み範囲に限り反復可能 |
| ⑥ 確定版 | ユーザーOK後、レビュー用設定の整理・バージョン整合 | 確定指示後 |
| ⑦ main・本番 | 差分確認後main統合・本番デプロイ | main反映と本番公開の権限を確認 |
| ⑧ 記録 | 変更点・不要コード整理・コミット・テスト・公開結果の報告 | 実施済みと未確認を区別 |

作業権限は段階別に管理する。「見て・解析して・整理して・どう思う」は読み取りまたは提案のみ。「実装して」は指定範囲のコード変更のみ。「レビュー版を公開して」は指定レビュー先の公開のみ。「確定して・mainへ反映して」は対象版を確認して実施する。「本番公開して」は本番配信の承認とする。**曖昧な「うん」「OK」「進めよう」だけでは、変更対象と作業範囲が明確でない限り次段階の承認としない。**

## 3. 実装と品質

- 関連モジュール、書き込み入口、イベント発火、参照先、共通Store、差分同期を事前調査する。
- 既存処理に別経路を重ねて回避せず、責務単位で整理する。不要になった旧実装を掃除する。
- Rendererは描画、Controllerは操作、Storeは保持・変更、永続化・同期は対応する責務に分離する。ファイルを細かく分けること自体を目的としない。
- 変更がレコードID、データ構造、Firestore、OneDrive、オフライン、競合解決、サービスワーカーに及ぶ場合は既存データ・複数端末・再起動を含めて影響を評価する。
- 変更した箇所と周辺機能をテストし、未実施の実機検証は「未確認」と記載する。
- 想定外の問題が発生しても、勝手に別機能やデプロイワークフローまで修正しない。

## 4. GitHubブランチ・バージョン

- `main`：確定版・本番。直接編集を原則避け、承認済みの内容だけを反映する。
- `work`：通常の実装・レビューで**1本を継続利用**する。確定後は未確定変更を確認して最新mainへ合わせる。強制更新は別途承認が必要。
- `feature/xxx`、`fix/xxx`：並行開発や独立した修正が必要なときだけ追加する。分岐した機能を意図せず混在させない。
- レビュー段階の英字枝番（A/B/C等）は常設の命名ルールではない。必要時にその都度決める。
- 確定版は本番公開成功後にバージョンタグで記録する。タグは原則として移動・削除しない。同じ版への後日修正は別のリビジョン等で履歴を区別する。
- 古いブランチは一括削除しない。統合済み／未統合で必要／不要候補に分類し、削除前に差分と保管状況を示して承認を得る。
- GitHubへのpush、ブランチ作成、PR、タグ作成、ブランチ削除も許可範囲内でのみ行う。

## 5. レビューURLとデプロイ

**通常開発で従来使用していたURL：**  
`https://odako-chousa-system-pwa--v0163a-djc70l4o.web.app/app.html`

**一時的な分岐レビューで使用したURL（通常開発用ではない）：**  
`https://odako-chousa-system-pwa--review-photo-pdf-amypbo0x.web.app`

- 通常開発は原則として従来のレビューURLを継続利用する。ただし、実際のHostingサイト・チャンネル、有効期限、公開権限、既存ブランチとの対応は**初回の公開前に読み取り確認**する。
- ブランチ名・バージョン変更を理由にレビューURLを変更しない。並行開発ではレビュー先の競合を回避する。
- pushによるGitHub Actionsの自動デプロイを事前に調べる。レビュー公開と本番公開を混同しない。
- 現行構成ではmainへのpushでFirebase live公開が自動起動するため、**main更新は本番公開につながる操作**として扱う。自動連動を変更する場合も別途承認を得る。
- デプロイ前にブランチ、プロジェクト、Hostingサイト・チャンネル、公開URLを確認する。公開後にテスト・Actions結果・配信バージョン・Service Workerキャッシュを確認する。
- 失敗時はまず原因と追加修正案を報告し、承認範囲外の設定変更や再デプロイをしない。

## 6. 定期的な全体整理と仕様書

- 通常の小修正とは別に、必要な段階で現行コード全体・依存関係・重複処理・旧コード・潜在不具合を調査する。
- ChatGPTとClaudeで独立したレビューを行い、互いの指摘を現行コードに照らして検証する。Claudeの提案をそのまま採用せず、修正計画を合意してから実装する。
- 全体整理では既存挙動を維持し、リファクタリングと仕様変更を混ぜない。
- 仕様書は機能がまとまって確定した段階や全体整理時に更新する。現行コードとの違いを明示し、実装済み・構想中を区別する。どちらを正とするか判断に迷う場合は確認する。

## 7. 完了報告と運用変更

完了報告には、目的・変更ファイル・修正内容・整理した旧処理・コミット・テスト・未確認事項・レビュー先・本番先・バージョンを含める。コード変更、GitHub反映、Firebase公開、実機確認を混同しない。

このルール自体も運用しながら改善してよいが、内容の変更にはユーザーと合意する。文書更新だけの依頼を、アプリ本体の修正や本番公開の許可とみなさない。
